# Enforce CSRF protection on login and signup

## Status and handoff

2026-11-26. The merge of `origin/main` at `b89f956` into `fix/auth-csrf` remains in progress with its resolutions staged. Both test entry points ran the migrated CSRF tests. The development CORS and throttle checks passed, and disposable resources were removed. The next action is independent re-review of the staged tree.

## Objective, context, and scope

Require Django CSRF validation before either `POST /api/login/` or `POST /api/signup/` can authenticate credentials, create an account, or start a session. Restrict development credentialed CORS to the documented frontend origin, `http://localhost:5173`. Preserve the existing endpoints, JSON request and success response shapes, credential and signup validation, session authentication, throttles, and signup side effects. The existing form parsers can remain available under CSRF protection.

The expected changes are in [library views](../../bookclub/library/views.py), [library tests](../../bookclub/library/tests/), and [development settings](../../bookclub/mysite/settings/development.py). The frontend already follows the required token flow. This work requires no schema migration or new dependency. Broader authentication changes, production cookie or origin changes, infrastructure changes, and deployment are outside this plan. Deployment and external service access require separate authorization under [AGENTS.md](../../AGENTS.md).

## Discoveries and decisions

- **2026-11-26 — Anonymous login and signup lack server-side CSRF enforcement.** Both [routes](../../bookclub/library/urls.py) resolve directly to DRF `APIView` classes with `AllowAny` and no explicit CSRF protection. `APIView.as_view()` exempts the outer callback from the configured Django CSRF middleware. Default `SessionAuthentication` returns before its CSRF check for anonymous requests. Login explicitly authenticates credentials and establishes a session. Signup creates a user and system lists, schedules welcome email after commit, and establishes a session. The default parsers accept browser form submissions, so production's CORS allowlist cannot substitute for CSRF enforcement. The source establishes the missing check and the risk of an unintended account session or signup. Deployed behavior and browser impact were not verified. [Pinned DRF views](https://github.com/encode/django-rest-framework/blob/3.18.2/rest_framework/views.py) · [Pinned DRF authentication](https://github.com/encode/django-rest-framework/blob/3.18.2/rest_framework/authentication.py) · [Pinned DRF defaults](https://github.com/encode/django-rest-framework/blob/3.18.2/rest_framework/settings.py)
- **2026-11-26 — Development permits credentialed CORS from every origin.** Development sets `CORS_ALLOW_ALL_ORIGINS = True` and inherits `CORS_ALLOW_CREDENTIALS = True` from [base settings](../../bookclub/mysite/settings/base.py). This overrides the local origin allowlist and permits cross-origin reads of API responses, including the token bootstrap response, subject to browser network and cookie rules. Development's CSRF trusted origins are already explicit. [Production settings](../../bookclub/mysite/settings/production.py) use exact CORS and CSRF origin lists and secure `SameSite=None` cookies. No production settings weakness was established in this review. [django-cors-headers 4.9.0 configuration](https://github.com/adamchainz/django-cors-headers/tree/4.9.0#configuration)
- **2026-11-26 — The client already supplies a token.** [The shared client](../../frontend/src/api/client.ts) fetches a masked token from `GET /api/csrf/` with credentials and sends `X-CSRFToken` with unsafe requests. [The auth client](../../frontend/src/api/auth.ts) clears the cached token after login or signup, and the shared client clears it on a `403` without replaying the request. Django rotates the CSRF secret when either endpoint signs the user in. The current signup test uses `APIClient()` with CSRF checks disabled and verifies business behavior only. Use Django's `csrf_protect` on each view's `dispatch` so the check runs inside DRF's exempt outer callback. Verify the resulting Django `403` through the existing frontend error path. [Django 6.0 CSRF reference](https://docs.djangoproject.com/en/6.0/ref/csrf/) · [DRF APIClient CSRF testing](https://www.django-rest-framework.org/api-guide/testing/#csrf-validation)
- **2026-11-26 — The browser run uses separate local settings.** Build from staged source in a separate Compose project with tmpfs PostgreSQL. The browser settings import development, restore the base login and signup throttle rates, and use an in-memory cache and broker. The welcome task is mocked. Docker Desktop did not publish the web port on the internal network alone. The disposable web service also uses a bridge and publishes only to host loopback. PostgreSQL stays on the internal network with no published port.
- **2026-11-26 — The CORS probe needs a local cache.** The first standalone process could not import the staged source until `PYTHONPATH=/app` was supplied. The next run reached the token view and found that its DRF throttle requires a cache. The probe uses a local-memory cache with the actual development CORS settings.
- **2026-11-26 — Integrate the suites under `library.tests`.** Move the six auth CSRF tests into `test_auth_csrf.py`, the four search tests into `test_search.py`, and the two older review tests into `test_reviews.py` alongside the class from `main`. Keep the existing auth, list, and review cases from `main`. Its auth tests now bootstrap a token before submitting credentials or logging out. Keep the AI app test and remove the former `library/tests.py` to give both test entry points one library package to discover.
- **2026-11-26 — Preserve the auto-merged settings and entry points.** The merge retains the local CORS and CSRF origin and brings in `main`'s development throttle update. Keep the isolated launcher, staging rules, test Compose file, and CI test command. Combine the setup and test runbooks with the feature, API, and deployment documentation, and update architecture links to the package.
- **2026-11-26 — Restore the migrated review fixture's user model lookup.** The first isolated run discovered the package and ran the CSRF cases, but the older review class failed in fixture setup because its move left `User` undefined. Use `get_user_model()` in that fixture, as the neighboring review class does, and rerun both entry points.

The reviewer found no actionable defect in the endpoint or CORS implementation. The finding is addressed by moving the tests into the package and verifying both entry points.
